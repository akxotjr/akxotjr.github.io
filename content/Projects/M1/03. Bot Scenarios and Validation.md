## Headless Client Flow

`M1_Bot`은 account `6000`부터 순서대로 headless client를 만든다. 각 Bot은 password credential으로 connect한 뒤 Ready 상태에서 character list, 첫 character select, world entry를 차례로 요청한다. world participant가 생기면 scenario가 running 상태가 되어 chat과 movement를 시작한다.

```text
connect -> Ready
    -> character list -> first character select
    -> world entry -> participant available
    -> chat / movement / portal scenario
```

Bot은 character content response의 request ID와 FlatBuffers payload를 검증한다. disconnect, request rejection, content rejection, invalid payload, character 없음은 scenario failure로 기록한다.

## Profiles

| Profile | Chat | Movement and portal |
| --- | --- | --- |
| `baseline` | 10 s, 64 byte; Global 30%, World 50%, Direct 20% | Traverse + distributed portal |
| `target` | 10 s, 64 byte; World 80%, Direct 20% | Traverse + distributed portal |
| `peak` | 2 s, 64/128 byte 교대; Global 40%, World 50%, Direct 10% | Traverse + distributed portal |
| `stress` | 1 s, 128 byte; Global 50%, World 50% | Traverse + distributed portal |
| `aoi-hotspot` | disabled | Cluster Square, portal disabled |
| `portal-burst` | disabled | idle, measurement 시작 때 synchronized portal |

BotRunner는 world contents에서 static instance, portal approach position, traverse lane, hotspot을 로드한다. non-custom profile의 첫 world는 Bot index에 따라 static instance 목록에 분산한다. Direct cohort는 ring 방식으로 다음 Bot character name을 recipient로 사용한다.

## Movement Scenarios

### Traverse

Traverse는 assigned lane과 initial phase에서 시작해 이동, idle, 반대 방향 이동, idle을 반복한다. 이동 intent는 500 ms heartbeat로 다시 제출된다. Distributed portal mode에서는 world stay deadline 뒤 authored portal approach position으로 이동하고, transition 뒤 다음 world에서 scenario를 재개한다.

### Cluster Square

AOI hotspot profile은 data에 정의된 hotspot 안으로 먼저 이동한 후 `W → A → S → D` directional intent를 반복한다. 이동 시간은 configured duration과 hotspot half extent에서 계산한 상한 중 작은 값을 사용한다. 이 profile은 portal 대신 같은 AOI 영역의 지속적인 movement replication을 만든다.

### Portal Handling

portal approach의 destination이 직전 world가 아닌 route를 우선 선택한다. expected destination으로 world가 바뀌면 portal transition count를 증가시키고, 다른 world가 열리면 unexpected transition으로 기록한다. deadline이 지나면 timeout을 기록하고 설정된 연속 timeout 한도까지 approach intent를 재시도한다.

## Execution Phases and Output

CLI는 `baseline` 또는 `<target|peak|stress|aoi-hotspot|portal-burst> <botCount>`를 받으며 Bot 수는 1–4000이다. connect rate는 100 Bot/s, random seed는 1로 고정된다.

| Phase | Current duration | Meaning |
| --- | --- | --- |
| Ramp-up | scheduled connection time + 최대 5 min settle | 모든 Bot이 running 또는 failed가 될 때까지 연결 |
| Warm-up | baseline/`--fast`: 1 min; 그 외: 5 min | steady-state 전 안정화 |
| Measurement | baseline/`--fast`: 3 min; 그 외: 30 min | scenario 관측 구간 |
| Cool-down | measurement 뒤 | 모든 Bot의 graceful disconnect와 runtime shutdown |

각 phase 시작/종료는 `[Phase]` log에 wall-clock `unix_ns`로 기록된다. Bot 상태 출력에는 ready, in-world, running/failed, chat 송수신·거부, portal transition/timeout, unexpected world transition이 포함된다.

Server는 5초 window의 `MetricsAggregator` output을 `logs/metrics`에 기록한다. 구체적인 scope와 key는 [[Projects/Jam/Observability/03. Metric Catalog|Metric Catalog]]를 참조한다.

## Interpretation Boundary

Bot은 protocol, server ownership, simulation, AOI, replication과 portal 흐름의 headless 부하를 만드는 도구다. Unity rendering, camera, input UX나 client prediction correctness를 검증하지 않는다. 또한 profile은 현재 `BotRunner`에 하드코딩된 workload이므로 서비스 SLO나 capacity 보장을 의미하지 않는다.
